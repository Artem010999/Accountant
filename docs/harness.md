# Харнесс: как проверять фронтенд по дизайну

Харнесс — набор команд и соглашений, с помощью которых любой агент или человек может повторить гейты из `docs/quality-gates.md` без догадок.

## 1. Что поднимаем

| Что | Команда | Адрес | Зачем |
|---|---|---|---|
| Эталон (дизайн) | `cd design/project && py -m http.server 8001 --bind 127.0.0.1` | http://127.0.0.1:8001/<Имя>.dc.html | скриншоты эталона |
| Наш фронтенд | `npm run dev -w @passport/frontend` (или `preview_start` с именем `frontend` из `.claude/launch.json`) | http://localhost:5173 | скриншоты реализации |
| Тесты | `npm test` из корня | — | T2 |

Эталон не требует `support.js`: статичная разметка с inline-стилями отрисовывается сама. Скрипты `<script type="text/x-dc">` в конце файлов — логика прототипа, её поведение проверяется по тексту дизайна и user-flows.

## 2. Скриншоты

- Ширина окна 1440 px (`resize_window` с custom width 1440, height 900). Для длинных экранов — полная высота страницы.
- Имена: `frontend/.visual/<stage>-<screen>-{ref,ours}.png`, например `G1-main-ref.png`, `G1-main-ours.png`.
- Эталон и реализация снимаются в одинаковом состоянии (та же прокрутка, тот же текст).
- Папка `frontend/.visual/` в `.gitignore`.

## 3. Порядок сверки одного экрана

1. Открыть эталон, снять `ref`.
2. Открыть наш маршрут, снять `ours`.
3. Сравнить глазами по критерию V1 из `quality-gates.md`, отметить расхождения списком «элемент — что не так — где в CSS/разметке».
4. Исправить, повторить 2–3 до пустого списка.
5. `get_page_text` на нашем экране, сверка строк с `*.dc.html` (V2): заготовка скрипта — `grep -o` по тексту эталона.
6. Записать результат в отчёт этапа: экран, статус, пути к скриншотам, остаточные расхождения.

## 4. Соглашения по тестам

- Тесты рядом с кодом: `Экран.test.tsx`.
- Проверяем поведение и тексты, а не внутреннюю вёрстку: роли, подписи, маршруты, состояния.
- Для каждого маршрута этапа — хотя бы один тест рендера (ключевой заголовок из дизайна присутствует).
- Для сценариев — тесты переходов (user-event): клик → переход/состояние.
- Не используем снимки DOM (`toMatchSnapshot`) как замену проверке дизайна: они не доказывают совпадение с эталоном.

## 5. Правила владения файлами

- Каждая группа работает только в `frontend/src/features/<группа>/` и `frontend/src/features/<группа>/...`.
- Общее (`shared/styles`, `shared/ui`, `app/routes.tsx`) меняется только на этапе G0 или отдельным согласованным изменением, которое фиксируется в отчёте.
- Не трогаем `backend/`, `packages/`, `design/` (дизайн — read-only).

## 6. Типичные причины расхождений (чек-лист при сверке)

- Шрифт не Onest или нет веса 800 — проверить `<link>` и `font-weight` в эталоне.
- Межстрочный интервал: эталон задаёт `line-height` в px или в числах — сохранять как в эталоне.
- Тени и границы: часто `1px solid #E4E4E7` и отдельная тень — переносить точно.
- Отступы: эталон использует `gap` и `padding` в px; не заменять на «похожие» значения.
- Текст: кавычки «ёлочки», неразрывные пробелы, тире — дословно из эталона.
